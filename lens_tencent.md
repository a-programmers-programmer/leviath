## Verdict: StepInput / StepOutput — MERELY-ACCEPTABLE

The names are functional and self-describing, which is a genuine improvement over the opaque dataflow jargon of `Port`. A reader encountering `StepInput` or `StepOutput` in a schema or UI will immediately understand "this is something a step consumes" or "this is something a step produces." That clarity is real and valuable.

However, the "Step" prefix carries a hidden cost: **contextual redundancy**. In any GraphQL schema, these types will almost certainly appear as the return types of fields nested under a `Step` type — e.g., `Step.inputs: [StepInput!]!` and `Step.outputs: [StepOutput!]!`. In that position, the "Step" prefix is pure noise; the parent type already establishes the context. A strong reviewer should ask: are `StepInput` and `StepOutput` ever referenced *outside* the shadow of a `Step` type? If they appear as top-level query return types, in union members, or as arguments to mutations that are not step-scoped, then the prefix earns its keep. If they are strictly step-scoped, the names are unnecessarily verbose and `Input`/`Output` (or, since those are dangerously generic for a global GraphQL namespace, `StepInput`/`StepOutput` is a pragmatic compromise) would be preferable.

A secondary concern: the names conflate **structural role** with **semantic role**. In a workflow engine, a step's input slot isn't just "an input to a step" — it's a binding point, a variable declaration, a data contract. `StepInput` flattens all of that into a single noun phrase. If the type shape includes fields like `name`, `type`, `required`, `defaultValue`, then the name `StepInput` undersells the richness of the concept. A name like `StepParameter` or `StepSlot` might better capture that the object is a *declaration* rather than a *value*. That said, `StepInput` is not wrong — it's just not maximally precise.

**Type shape concern:** Without access to the actual schema file (the working-directory sandbox prevented reading it), I must flag that if `StepInput` and `StepOutput` share significant structural overlap (e.g., both have `name`, `type`, `description`), they should likely implement a common interface such as `StepIO` or `StepSlot`. If they are defined as entirely separate types with duplicated fields, that is a shape problem a reviewer should call out regardless of the naming.

## Verdict: WorkflowDiscoveryResult — BAD

This name fails on three independent grounds: **verbosity**, **metaphor mismatch risk**, and **prefix redundancy**.

**Verbosity.** At 24 characters, `WorkflowDiscoveryResult` is a mouthful. GraphQL type names appear in queries, introspection output, generated TypeScript types, and documentation indexes. Long compound names create friction at every touchpoint. Compare: `MatchResult` (11 chars) vs. `WorkflowDiscoveryResult` (24 chars). The new name more than doubles the character count without a commensurate increase in semantic precision.

**Metaphor mismatch risk.** "Discovery" and "matching" are different user mental models. "Matching" implies: I have a concrete task; the system finds workflows that fit. "Discovery" implies: I am exploring or browsing to find something I didn't know existed. If the actual operation is closer to search/query/match (the old name `MatchResult` suggests it was), then "Discovery" is a misleading rebrand that sets incorrect user expectations. A user who "discovers" a workflow may expect recommendations, browsing interfaces, or serendipitous results — not a deterministic match against task parameters. The author's rationale ("the user-facing action is 'discovering a workflow for a task'") may itself be wrong: the user's goal is to *find the right workflow*, and whether that's called matching, searching, or discovering is secondary to what the system actually does. The name should reflect the *operation*, not a marketing verb.

**Prefix redundancy.** The "Workflow" prefix is almost certainly redundant. If this type is returned by a query like `discoverWorkflows` or sits in a `Workflow`-namespaced section of the schema, the "Workflow" prefix adds no disambiguating power. A name like `DiscoveryResult` would be shorter and equally clear in context. If the type is used as a union member alongside non-workflow discovery results, then the prefix is justified — but that seems unlikely.

**Recommended alternatives (if the team insists on the "discovery" metaphor):** `DiscoveryResult` (drop the redundant "Workflow"), or if the operation is really about matching, `WorkflowMatch` (shorter, no "Result" suffix needed if the query name already implies a result). If neither metaphor is quite right, the neutral `WorkflowSearchResult` at least avoids the semantic baggage of "discovery."

**Type shape concern:** A type named `WorkflowDiscoveryResult` should ideally be a thin wrapper — e.g., containing a `workflow` field, a `confidence` or `score` field, and perhaps match rationale. If the type shape instead embeds the entire workflow object inline (duplicating the `Workflow` type's fields), that's a normalization problem. A reviewer should verify that the result type *references* a `Workflow` rather than *redefining* it.
